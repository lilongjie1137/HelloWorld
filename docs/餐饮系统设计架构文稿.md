## 1. 业务范围与系统定位

系统本质：**连锁餐饮的「点餐 POS + 出品分流 + 收银」中台 + SaaS 平台**，覆盖总部管控与多门店运营。

核心能力域：
- **交易**：开台 → 点单（炒菜 + 饮品混合）→ 出品分流打印 → 收银 → 清台。
- **出品**：后厨热菜间 / 吧台各自收单，互不干扰；P2 增加杯贴与厨显。
- **自助**：P2 微信扫码点单。
- **经营**：P3 会员、营销、深度报表。
- **连锁管控**：总部统一管理商品、价格策略、门店、权限；门店执行运营。

## 2. 技术栈选型（明确推荐）

### 2.1 后端：**Go（go-zero 微服务）** —— 推荐

理由（针对本项目特点）：
1. **每家门店都要一个本地打印/点单网关**，Go 编译成**单一静态二进制**，丢到门店一台迷你主机即可跑，无 JVM/运行时依赖，运维最省心——这是连锁场景的决定性优势。
2. **云端与边缘同语言**：订单、商品、打印任务等模型可在云/边共享代码，降低团队认知负担与重复实现。
3. **高并发、低资源**：连锁多门店并发出单、扫码点单峰值场景下，Go 协程模型表现优秀，服务器成本低。
4. go-zero 自带 RPC、API 网关、限流熔断、代码生成，适合中小团队快速搭微服务。

> 备选：若团队更偏业务系统且 Go 人手不足，可用 **Java Spring Cloud Alibaba**（餐饮 SaaS 经典选择，生态成熟、招聘容易），但门店边缘网关仍建议用 Go 单二进制实现。**本文后续以 Go 方案为主线。**

### 2.2 各端与中间件

| 角色 | 选型 | 说明 |
| --- | --- | --- |
| 后端核心 | **Go + go-zero** | 微服务 + API 网关 |
| 门店边缘网关 | **Go 单二进制** | 本地打印队列 + 离线点单缓存 |
| 收银/点单端 | **Android 平板**（Kotlin 原生，或 Flutter） | 主力交易端，需离线能力 |
| 顾客端 | **微信小程序**（Taro/uni-app，可同时出 H5） | P2 扫码点单 |
| 厨显 KDS | Web（大屏浏览器，Vue3） | P2 |
| 管理后台 | **Vue3 + Element Plus** | 总部/门店商品、报表、配置 |
| 关系库 | **MySQL 8** | 交易主库，按门店/租户分库分表预留 |
| 缓存 | **Redis** | 桌台状态、会话、热点商品、分布式锁 |
| 消息队列 | **Kafka / RocketMQ** | 打印任务、订单事件、外卖回调、报表/营销订阅 |
| 实时 | **WebSocket**（云↔端）；门店内设备可选 MQTT | 厨显、收银状态同步 |
| OLAP | **ClickHouse**（P3） | 深度报表、销量排行 |
| 对象存储 | OSS/S3 | 商品图片、票据归档 |
| 网关/部署 | Nginx + Docker + K8s（云端） | 门店边缘用 systemd/docker 单机部署 |

## 3. 总体架构（云端 + 门店边缘混合）

```
                         ┌───────────────── 云端 (SaaS 平台) ─────────────────┐
  总部管理后台(Vue3) ────▶│  API 网关 (go-zero gateway)                        │
  门店管理后台(Vue3) ────▶│   ┌────────┬────────┬────────┬────────┬─────────┐  │
  微信小程序(顾客,P2) ───▶│   │租户/门店│商品中心│ 交易    │收银支付│会员营销 │  │
                         │   │权限服务 │服务     │(桌台/点单)│服务   │(P3)     │  │
                         │   └────────┴────────┴────────┴────────┴─────────┘  │
                         │   报表服务(P3)  打印路由服务  外卖对接(P2)           │
                         │   MySQL  Redis  Kafka  ClickHouse(P3)  OSS          │
                         └───────────┬───────────────────────────┬────────────┘
                                     │ HTTPS/WSS (公网)            │
            ┌────────────────────────▼──────┐      ┌──────────────▼───────────────┐
            │ 门店A 边缘网关(Go单二进制)      │      │ 门店B 边缘网关 ...             │
            │  ├ 本地打印队列(重试/回执/补打) │      │                               │
            │  ├ 离线点单缓存(弱网兜底)       │      │                               │
            │  └ 局域网设备:                  │      │                               │
            │     后厨打印机/吧台打印机/杯贴机 │      │                               │
            └──────────┬─────────────────────┘      └───────────────────────────────┘
                       │ 局域网
       Android收银平板 ─┴─ 厨显KDS(P2) ─ 网络打印机(ESC/POS) ─ 标签机(TSPL,P2)
```

设计要点：
- **云端**：多租户 SaaS，承载所有持久化、连锁管控、跨店数据。
- **门店边缘网关**：保证**弱网/断网时门店内点单、出单、现金收银不中断**；网络恢复后与云端对账同步。
- **Android 平板**：优先连本店边缘网关（局域网，低延迟、抗断网），网关再与云端同步。

## 4. 多租户 / 连锁模型

连锁层级：

```
租户(Tenant/品牌)
 └─ 总部(HQ)
     ├─ 区域/分公司 (可选)
     └─ 门店(Store) ──┐
                      ├─ 桌台区/桌台
                      ├─ 出品部门(后厨热菜间/吧台/凉菜...)
                      ├─ 设备(收银平板/打印机/标签机)
                      └─ 员工(收银/服务员/后厨/店长)
```

数据隔离与共享：
- **隔离维度**：所有业务表带 `tenant_id` + `store_id`。起步用「共享库 + 行级隔离」，规模上来后按租户分库。
- **总部下发、门店执行**：
  - **商品/价格策略**在总部维护，支持「全国统一」或「门店可调价」两种模式（门店级价格覆盖表）。
  - **菜单适用范围**：商品可配置适用门店集合（连锁不同店菜单不同）。
- **跨店能力**：会员、储值、券（P3）跨店通用；报表支持单店/区域/全品牌维度。

## 5. 服务（模块）划分

P1 以**少量服务 + 清晰边界**起步，避免过度拆分：

| 服务 | 职责 | 期 |
| --- | --- | --- |
| 租户/门店/权限服务 | 租户、门店、员工、RBAC、交接班 | P1 |
| 商品中心服务 | SPU/SKU、属性组(规格/做法/加料)、出品部门、价格策略、菜单适用范围 | P1 |
| 交易服务 | 桌台(开台/转桌/并桌/一桌多单)、点单、加退菜、订单生命周期 | P1 |
| 打印路由服务 | 拆单、打印任务编排、与边缘网关交互、补打 | P1 |
| 收银支付服务 | 现金、扫码枪、折扣、账单；P2 聚合支付/自动清台 | P1→P2 |
| 边缘网关(Go) | 本地打印执行、离线点单、设备管理 | P1 |
| 外卖对接服务 | 美团/饿了么接单、菜品映射、状态回传 | P2 |
| 会员营销服务 | 会员、储值、券、营销活动 | P3 |
| 报表服务 | 账单/销售统计/销量排行（ClickHouse） | P3 |

服务间：同步用 gRPC，异步/事件用 Kafka（如「订单已下单」事件 → 打印路由 / P3 报表&营销订阅）。

## 6. 核心领域模型

### 6.1 商品（第一期地基，融合炒菜与饮品的关键）

```
SPU 商品 (鱼香肉丝 / 珍珠奶茶)
 ├ tenant_id, 适用门店范围
 ├ production_dept_id  出品部门 → 决定打到后厨/吧台
 ├ 基准价 / 是否套餐 / 是否称重
 └ ModifierGroup[] 属性组
      ├ group_type = SPEC   规格(单选,必选,可改基准价)  例:大杯/中杯/扎
      ├ group_type = METHOD 做法(单/多选,不加价)        例:去冰/少冰、半糖/全糖、免葱/少辣
      └ group_type = ADDON  加料(多选,单独加价)          例:加珍珠+3、加椰果+3

ModifierOption 选项
 ├ name, group_id
 ├ price_delta  (SPEC可定价/加价, ADDON加价, METHOD=0)
 └ 排序/默认选中/是否可用
```

价格策略（连锁）：`SPU 基准价` + `门店价格覆盖表(store_id, spu_id, price)`，按门店是否允许调价生效。

### 6.2 订单（下单即快照，防止改价污染历史）

```
Order 订单
 ├ tenant_id, store_id, table_id, 单号
 ├ status: 待下单/已下单/部分上菜/已结/已清台/已退
 ├ source: 服务员POS / 顾客小程序 / 外卖(P2)
 └ OrderItem[] 订单行
      ├ spu 名称/分类 快照
      ├ 选中 SPEC(大杯) / METHOD[去冰,半糖] / ADDON[{加珍珠,+3}]
      ├ 单价 = 规格基准价 + Σ加料加价
      ├ 数量 / 小计 / 备注
      ├ production_dept_id 快照（供打印路由）
      └ item_status: 待制作/已起菜/已上菜(P2)
```

桌台：`Table` 带状态机（空闲/占用/已开台/待清台）；支持转桌（改 table_id）、并桌（多桌合一单）、一桌多单（一桌多 Order）。

### 6.3 打印任务

```
PrintJob
 ├ store_id, order_id, 目标设备(printer_id) / 出品部门
 ├ type: 后厨小票 / 吧台小票 / 杯贴标签(P2) / 结账单 / 退菜单
 ├ payload (排版内容)
 ├ status: 待打/已下发/已打印/失败
 └ 重试次数 / 回执时间
```

## 7. 分单打印与本地网关设计（P1 关键）

**目标**：鱼香肉丝→后厨热菜间，珍珠奶茶→吧台，互不干扰、可靠出单。

机制（配置驱动，非写死）：
1. 商品归属 **出品部门**；打印机绑定 **出品部门 + 票型**。
2. 下单后，**打印路由服务**按订单行的 `production_dept_id` 分组 → 每组生成 `PrintJob` → 投递到该店边缘网关。
3. **边缘网关**维护本地打印队列：调用对应网络打印机（ESC/POS 小票），失败重试，回传打印回执；支持补打、退菜打印。
4. **P2 杯贴**：吧台增配标签机（TSPL/CPCL），出单打印「桌号-品名-去冰半糖」不干胶。

可靠性设计：
- 打印任务先落库 + 进队列，**至少一次投递 + 幂等**（防重复打印用 job 唯一键）。
- 边缘网关断网时本地排队，恢复后续打并回执。
- 打印机离线/缺纸状态上报，收银端可见并支持改派/补打。

## 8. 离线 / 弱网策略（餐厅生命线）

分级保障：
- **L1 局域网内可用**：Android 平板 + 边缘网关在店内局域网即可完成点单、出单、现金收银，即使公网断开。
- **L2 数据最终一致**：边缘网关缓存离线期间的订单/收银流水，公网恢复后与云端同步、对账。
- **L3 冲突处理**：以「订单单号 + 操作序列」幂等合并；现金账以门店为权威源，云端补录。

> 聚合支付（P2）依赖公网，断网时降级为现金/扫码枪，恢复后补单。

## 9. 实时通信

- **云 ↔ 端**：WebSocket（WSS）。用于厨显 KDS 接单/起菜/上菜状态、收银端订单状态同步、小程序下单推送到吧台。
- **门店内设备**（可选）：MQTT，用于打印机/厨显等设备状态与指令低延迟分发。
- 事件驱动：订单状态变更走 Kafka，KDS/收银/报表多方订阅。

## 10. 微信小程序点单（P2）

流程：
1. 顾客扫桌贴二维码（携带 store_id + table_id）→ 打开小程序菜单。
2. 复用 P1 商品模型：饮品自选 **规格/冰度/甜度/加料**，炒菜选做法/备注。
3. 提交 → 进入该桌当前订单 → 自动按出品部门分流打印（饮品直达吧台）。
4. 与服务员 POS 同桌共单，状态实时同步。

要点：小程序点单**完全复用 P1 的 SPU+属性组模型**，只是换了录入端，无需重构——这正是 P1 把模型做扎实的回报。

## 11. 权限与安全

- **RBAC + 数据范围**：角色（总部管理员/区域/店长/收银/服务员/后厨）+ 数据范围（按 tenant/区域/store 限定可见可操作）。
- **交接班**：班次内现金/账单归属，交接对账。
- **审计**：改价、退菜、反结账、删单等敏感操作留痕。
- **支付安全**（P2）：聚合支付走服务端下单 + 回调验签，金额服务端校验。
- 多租户隔离：所有查询强制带 `tenant_id`，防越权。

## 12. 部署拓扑

- **云端**：Docker + K8s；API 网关 + 各 go-zero 服务 + MySQL(主从) + Redis(集群) + Kafka + ClickHouse(P3) + OSS。
- **门店边缘**：一台迷你主机/工控机跑边缘网关（Go 单二进制，systemd 或 docker）；连接店内网络打印机、标签机、厨显、收银平板。
- **CI/CD**：GitHub Actions → 镜像构建 → 云端滚动发布；边缘网关版本远程灰度升级。

---

## 13. 数据与报表（P3）

- 交易库（MySQL）通过 binlog/CDC → Kafka → **ClickHouse**，承载深度报表。
- 报表：各类账单、销售统计、**菜品/饮品销量排行**、时段/门店/区域对比。
- 营销：基于会员 + 券，做「充值送饮品券」「会员饮品半价」；饮品高毛利可单独配置引流活动。
- 事件溯源友好：下单/支付/退款均以事件落 Kafka，报表与营销作为订阅方，互不阻塞交易主链路。

## 14. 三期落地路线

**V1.0 核心交易闭环**
- 租户/门店/员工/权限/交接班；多门店基础。
- 商品中心：SPU + 属性组（规格/做法/加料加价）+ 出品部门 + 价格策略。
- 桌台：开台/转桌/并桌/一桌多单。
- 点单：炒菜 + 饮品混合点单。
- 打印路由 + 边缘网关：后厨/吧台分流、可靠出单、离线兜底。
- 基础收银：现金、扫码枪、折扣。

**V2.0 效率与自助**
- 微信小程序扫码点单（自选冰度/甜度/加料，直达吧台）。
- 吧台标签机杯贴打印。
- 厨显 KDS：等叫/起菜/上菜。
- 聚合支付（自动清台）+ 外卖平台对接。

**V3.0 营销与报表**
- 会员、储值、券、饮品引流营销。
- ClickHouse 深度报表与销量排行。

## 15. 非功能性要求

| 维度 | 目标 |
| --- | --- |
| 可靠性 | 门店断网仍可点单/出单/现金收银；打印至少一次且幂等 |
| 一致性 | 交易强一致；离线数据最终一致 + 幂等合并 |
| 性能 | 单店高峰出单秒级；扫码点单峰值横向扩容 |
| 可扩展 | 多租户、可水平扩展、按租户分库预留 |
| 可运维 | 边缘网关单二进制、远程灰度升级、设备状态可观测 |
| 安全 | 多租户隔离、RBAC、敏感操作审计、支付验签 |

## 16. 待确认问题

1. **价格模式**：连锁是「全国统一价」还是「门店可自主调价」？（影响价格策略表设计）
2. **会员/储值**是否要求 P1 就预留数据结构（即使功能 P3 才上）？
3. **小程序支付主体**：用品牌统一商户号，还是各门店独立商户号结算？
4. **外卖平台**（P2）要对接哪些（美团/饿了么/抖音）？
5. **边缘网关硬件**：门店是否愿意放一台迷你主机？（若不愿意，可退化为云打印机方案，但弱网可靠性下降）
6. 后端是否接受 **Go** 方案，还是倾向 **Java Spring Cloud**（团队招聘/熟悉度考量）？
