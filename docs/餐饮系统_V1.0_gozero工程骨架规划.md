# 餐饮系统 V1.0 · go-zero 工程骨架规划

> 仅为**工程结构规划**（不含功能代码）。配套《V1.0详细设计》《接口清单》《ER与时序图》。
> 技术：Go + go-zero（API 网关 + RPC 微服务）、MySQL、Redis、Kafka；门店边缘网关为独立 Go 单二进制。

## 1. 总体工程形态

采用 **Monorepo（单仓多服务）**，便于共享 proto/model、统一 CI：

```
catering/                          # 仓库根
├── go.mod                         # 单 module(或 go workspace)
├── deploy/                        # K8s/Docker/compose、CI 脚本
├── common/                        # 跨服务共享库
│   ├── errcode/                   # 统一错误码
│   ├── response/                  # 统一响应包
│   ├── jwtx/                      # JWT 解析(tenant_id/employee_id/data_scope)
│   ├── interceptor/               # 多租户上下文、鉴权、数据范围
│   ├── mq/                        # Kafka 生产/消费封装
│   └── types/                     # 共享枚举(GroupType/OrderStatus...)
├── app/                           # 云端各服务
│   ├── gateway/                   # API 聚合网关(对外 REST)
│   ├── identity/                  # 租户/门店/员工/权限/交接班
│   ├── catalog/                   # 商品中心
│   ├── trade/                     # 桌台/点单/订单
│   ├── cashier/                   # 收银/账单/支付
│   └── printing/                  # 打印路由
├── edge/                          # 门店边缘网关(独立可单编译)
│   ├── cmd/edge-gateway/          # main, 单二进制入口
│   ├── internal/printq/           # 本地打印队列(ESC/POS, P2:TSPL)
│   ├── internal/offline/          # 离线点单/收银本地落库(SQLite/BoltDB)
│   ├── internal/sync/             # 与云端幂等上行/下行
│   └── internal/device/           # 打印机/设备驱动与状态
└── docs/                          # 设计文档(本系列)
```

> 也可用 **Go workspace（go.work）** 把 `app/*`、`edge`、`common` 拆成多 module，隔离边缘网关依赖。V1.0 先用单 module + 清晰目录即可。

## 2. 服务划分（go-zero）

每个云端服务 = 1 个 `*.api`（HTTP）+ 视需要 1 个 `*.proto`（RPC）。网关对外，内部服务间用 zRPC。

| 服务 | 形态 | 职责 | 依赖 |
| --- | --- | --- | --- |
| gateway | api | 对外 REST 聚合、鉴权、路由 | 各 rpc |
| identity | api+rpc | 租户/门店/出品部门/设备/员工/角色权限/交接班 | MySQL,Redis |
| catalog | api+rpc | 分类/SPU/属性组/选项/适用门店 | MySQL,Redis |
| trade | api+rpc | 桌台状态机/点单计价/订单/退菜；发 order.created | MySQL,Redis,Kafka |
| cashier | api+rpc | 结账/折扣/收款/清台/班次汇总 | MySQL,trade-rpc |
| printing | rpc+consumer | 消费 order.created→拆单→print_job→下发边缘 | MySQL,Kafka |

> V1.0 也可先做成 **模块化单体**（一个 go-zero api 服务内分 logic 包），把上面拆分作为「逻辑边界」，压力上来再拆进程——降低初期运维成本，与总体架构文稿一致。

## 3. 单服务内部结构（go-zero 规范，以 trade 为例）

```
app/trade/
├── trade.api                      # HTTP 接口定义(goctl 生成 handler/types)
├── trade.proto                    # RPC 定义(供 cashier 等调用)
├── etc/trade.yaml                 # 配置(DB/Redis/Kafka/zRPC)
├── internal/
│   ├── config/                    # 配置结构
│   ├── handler/                   # HTTP 路由(goctl生成)
│   ├── logic/                     # 业务逻辑
│   │   ├── table/                 # 开台/转桌/并桌
│   │   ├── order/                 # 下单/加菜/退菜/计价
│   │   └── ...
│   ├── svc/                       # ServiceContext(依赖注入:model/redis/mq/rpc client)
│   ├── model/                     # 数据访问(sqlx + 缓存, goctl model 生成)
│   ├── domain/                    # 领域逻辑(计价器 Pricer、桌台状态机)
│   └── mq/                        # order.created 生产者
└── trade.go                       # main
```

**计价器**（domain/pricing）伪逻辑：
```
unitPrice = (hasSpec ? specOption.price : spu.basePrice) + Σ addonOption.price
amount    = unitPrice * qty
// METHOD 选项不计价；所有选项与价格写入 order_item / order_item_modifier 快照
```

## 4. `.api` 草案（节选，trade 点单）

```
type (
  OrderItemReq {
    SpuId           int64   `json:"spuId"`
    Qty             int     `json:"qty"`
    Remark          string  `json:"remark,optional"`
    SpecOptionId    int64   `json:"specOptionId,optional"`
    MethodOptionIds []int64 `json:"methodOptionIds,optional"`
    AddonOptionIds  []int64 `json:"addonOptionIds,optional"`
  }
  CreateOrderReq {
    TableId int64          `json:"tableId"`
    Items   []OrderItemReq `json:"items"`
  }
  CreateOrderResp {
    OrderId     int64  `json:"orderId"`
    OrderNo     string `json:"orderNo"`
    TotalAmount string `json:"totalAmount"`
  }
)

@server(
  jwt: Auth
  prefix: /api/v1
  group: order
)
service trade-api {
  @handler CreateOrder
  post /orders (CreateOrderReq) returns (CreateOrderResp)

  @handler RefundItem
  post /orders/:id/items/:itemId/refund (RefundReq) returns (RefundResp)
}
```

> 用 `goctl api go -api trade.api -dir .` 生成骨架；`goctl model mysql ddl` 由建表 DDL 生成 model；`goctl rpc protoc` 生成 RPC。

## 5. 边缘网关（edge）模块规划

单二进制，门店迷你主机运行（systemd 或 docker）：

| 模块 | 职责 |
| --- | --- |
| device | 发现/管理网络打印机、标签机(P2)、状态采集(在线/缺纸) |
| printq | 本地打印队列：接收 print_job → ESC/POS 出单 → 重试 → 回执；job_key 幂等防重打 |
| offline | 弱网时本地落库(BoltDB/SQLite)订单与收银流水，本地拆单打印 |
| sync | 在线长轮询/WS 拉取打印任务；恢复后按 orderNo+opSeq 幂等上行；接收云端权威状态 |
| api(local) | 局域网内给 Android POS 提供下单/收银直连(在线转发/离线本地) |

通信：与云端 HTTPS/WSS；与店内打印机 TCP(9100, ESC/POS)。配置含 store_id、sn、云端地址、打印机清单。

## 6. 基础设施与横切

| 关注点 | 方案 |
| --- | --- |
| 多租户上下文 | 中间件从 JWT 解析 tenant_id/store_id/data_scope，注入 ctx；DAO 强制带 tenant_id |
| 鉴权/权限 | go-zero JWT + 自定义 interceptor 校验 permission code 与数据范围 |
| 配置 | etc/*.yaml + 环境变量；secrets 走 K8s Secret，不入库 |
| 日志/追踪 | go-zero 自带 logx + 链路追踪(trace id) |
| 缓存 | Redis：门店菜单、桌台状态、分布式锁(开台/结账防并发) |
| 事件 | Kafka topic: `order.created`/`order.settled`(P3报表/营销订阅) |
| ID | 雪花ID(分布式)；单号按 门店码-日期-序号 |
| 迁移 | DDL 版本化(golang-migrate)，建表脚本入 deploy/migrations |

## 7. 部署（deploy/）

- 云端：每服务 Dockerfile → 镜像 → K8s Deployment + Service；网关挂 Nginx/Ingress；MySQL 主从、Redis 集群、Kafka。
- 边缘：`edge-gateway` 交叉编译为门店主机架构二进制，systemd 托管；支持远程灰度升级 + 回滚。
- CI：GitHub Actions（lint: golangci-lint；test: go test；build & push 镜像）。

## 8. 建议开发顺序（待你下令开工）

1. `common` + `identity`（租户/门店/员工/权限）——一切的前提。
2. `catalog`（商品 + 属性组 + 计价模型）——P1 地基。
3. `trade`（桌台 + 点单 + 计价 + 发事件）。
4. `printing` + `edge`（拆单打印 + 边缘网关闭环）——验证「后厨/吧台分流」核心卖点。
5. `cashier`（结账收银清台 + 交接班）。
6. 离线/同步加固 + 联调。
